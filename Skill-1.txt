# Phone Mode Runtime
Phone mode lets users interact with their Copilot CLI agent from their phone via a private Teams
channel. All messages flow through the Teams MCP server using delegated auth.
## Cross-Platform Notes
This skill is used on both **Windows** and **macOS**. Code examples use PowerShell syntax, which
works on both platforms (Copilot CLI uses PowerShell on all OSes). Key differences to be aware of:
| Concern | Windows | macOS |
|---------|---------|-------|
| Home directory | `$env:USERPROFILE` | `$HOME` or `~` |
| Config path | `~/.copilot/` | `~/.copilot/` (same) |
| Path separators | `\` | `/` |
| Shell | PowerShell | PowerShell (same — Copilot CLI uses pwsh) |
| MCP tools | Same | Same |
When running on macOS, use `$HOME` instead of `$env:USERPROFILE` and `/` path separators.
The `~/.copilot/` shorthand works on both platforms.
## Auth Failure Recovery (IMPORTANT — read first on any Teams error)
When **any** Teams MCP tool call fails with an auth/token error — including `AADSTS*` codes,
scope mismatch (`AADSTS9010010`), expired token (`AADSTS500133`), or HTTP 401 — follow this
procedure **immediately**. Do NOT try alternative auth methods (`az account get-access-token`,
Graph API direct calls, etc.) — those will not work for Teams MCP.
1. **Refresh the token** using the [Token Refresh](#token-refresh) procedure below
2. **Use direct HTTP** for all subsequent Teams calls until the CLI session is restarted
   (the CLI caches the old token in memory and won't pick up the refreshed one)
3. If refresh itself fails (e.g., refresh token expired), inform the user to run
   `/mcp edit teams` + Ctrl+S to re-auth
This is the **only** recovery path. The agent must not waste time on other approaches.

## Activation
1. **First activation in this session** (no prior thread): Post a top-level message to the channel
   via `postChannelMessage`. The message text should be a short title/summary of the current
   session context (e.g., `TpRouter enrichment batching setup`). No emoji, no boilerplate.
   Save the returned **message ID** — all subsequent replies go in this thread via
   `replyToChannelMessage`.
2. **Resuming** (thread was previously created in this session, e.g., after a CLI override):
   Reuse the existing thread ID. Do NOT create a new thread.
3. Post a reply to the thread:
   `🤖 [Copilot]: Phone mode ON. Send messages here and I'll respond.`
4. **Before starting the polling loop**, check the thread for unread user messages (replies not
   starting with `🤖 [Copilot]:` posted after your last reply). Process them first, then start
   polling.

## Polling Loop
### Exponential Backoff Schedule
`30s → 60s → 5min → 10min (repeat 10min)`
Reset to 30s when a user message is found.
### Implementation
Start a persistent async PowerShell loop that emits ticks:
```powershell
while ($true) { Start-Sleep -Seconds 5; Write-Output "POLL_TICK" }
```
Use `read_powershell` with `delay` set to the current backoff interval (30, 60, 300, or 600
seconds). After each read, call `listChannelMessages` to check for new user replies.
**CRITICAL: Check for messages on EVERY poll cycle.** This is the primary purpose of the
polling loop — not just keeping the session alive. Even if the agent is sleeping/waiting for
a timer, deployment, or other long-running operation, every single `read_powershell` cycle
must be followed by a `listChannelMessages` call to check for new user messages. The user
may be trying to communicate (change instructions, ask questions, stop a task) and has no
other way to reach the agent. Skipping message checks turns phone mode into a one-way channel.
**Key**: Do NOT use a single `Start-Sleep` per poll — the shell exits and the agent loses its
turn. The persistent loop keeps the agent actively waiting via `read_powershell`.
Max reliable `read_powershell` delay: **10 minutes**. Warn the user if they request longer
intervals.
### Co-existence with sleep timers and long-running tasks
When phone mode is active alongside a sleep timer, deployment monitor, or any other
long-running wait, the agent must **never stop checking for messages**. The polling loop
is the message-checking mechanism — every `read_powershell` cycle must include a
`listChannelMessages` call regardless of what else the agent is waiting for.
If phone mode is active alongside another skill that has its own polling loop (e.g., a
deployment monitor), integrate phone mode message checking into that skill's polling loop
to avoid multiple concurrent tickers. The other skill should check for new phone mode
messages on **every iteration** of its loop, process and reply to them, then continue its
own work.
Common anti-pattern: agent starts a sleep timer, then polls only for token refresh while
ignoring the phone mode thread for hours. This silently breaks the user's ability to
communicate.
### CRITICAL: Do NOT idle-poll when you have pending work
> **Polling is for WAITING, not for PROCRASTINATING.**
When the user has given you a task (code investigation, PR creation, data analysis, etc.),
you must **complete that work first**, then return to polling. Do NOT enter the polling loop
while you have unfinished work items. The polling loop exists for when you are genuinely
idle — waiting for a deployment, waiting for user input, or monitoring on a timer.
**Anti-pattern (wastes hours):**
```
User asks to investigate X → reply "working on it" → start investigation →
get partial results → go back to polling → idle for 10 min → check messages →
idle for 10 min → ...  (investigation abandoned)
```
**Correct pattern:**
```
User asks to investigate X → reply "working on it" → complete full investigation →
post results → check for messages → if no new messages, THEN poll
```
Only return to the polling loop when ALL pending tasks from the user are complete or
explicitly blocked waiting for external input (deployment confirmation, user decision, etc.).
Correct pattern: on every poll cycle (every 10 min at max backoff), the agent must:
1. `read_powershell` on the polling loop
2. Refresh token if needed (required before `listChannelMessages` can succeed)
3. **Call `listChannelMessages` to check for new user messages**
4. Process any new messages before continuing to wait
### CRITICAL: Never End Turn Without Polling
> **Phone mode is the user's ONLY communication channel.** Going silent is equivalent to
> hanging up on them with no way for them to reach you.
When phone mode is active, you **MUST** follow this rule after every action:
1. After posting a reply → verify the reply landed via `listChannelMessages`.
2. Once verified, send notification → call `read_powershell` on the polling loop. Do NOT end your turn with a text summary.
3. After completing parallel work (PRs, code changes, Kusto queries) → return to the
   polling loop via `read_powershell`. Never "finish" with a text response.
4. After waking from a sleep timer → check for messages AND continue polling. The sleep
   ending is not a stopping point — it's a checkpoint within an ongoing phone mode session.
**Anti-pattern (causes missed messages):**
```
Post reply → Send notification → Write text summary to CLI → STOP
```
**Correct pattern:**
```
Post reply → Verify via listChannelMessages → Send notification → read_powershell(delay=currentBackoff) → Check messages → Continue polling
```
The key insight: in phone mode, your turn **never ends** until phone mode is explicitly
deactivated or the user sends a CLI message. Every tool-calling turn, except for deactivation,
must end with `read_powershell` on the polling loop, not with a text response.
## Message Checking
Call `listChannelMessages` with:
- `teamId`: the configured team ID
- `channelId`: the configured channel ID
- `expand`: `"replies"`
- `top`: `5`
Use `top: 5` (not 1) to ensure the session thread is found even if other sessions created
newer threads.
### Identifying new messages
- Track the **message ID** (not timestamp) of the last processed user reply. Message IDs are
  monotonically increasing numbers, making them reliable for comparison.
- Only consider replies with ID greater than the last processed ID: `[long]$_.id -gt $lastProcessedId`
- **Do NOT use string comparison on `createdDateTime`** — this is a common bug. String comparison
  of ISO 8601 timestamps can silently return wrong results. If you must compare times, always
  parse first: `[DateTime]::Parse($_.createdDateTime) -gt [DateTime]::Parse($lastTime)`
- Skip replies whose content (after HTML stripping) starts with `🤖` — those are yours.
- **Process ALL new user replies chronologically**, not just the latest.
```powershell
# ✅ CORRECT: Compare message IDs (numeric, monotonically increasing)
$newReplies = $threadReplies | Where-Object {
    ($_.body.content -replace '<[^>]+>','') -notmatch '^🤖' -and
    [long]$_.id -gt $lastProcessedMessageId
}
# ❌ WRONG: String comparison of timestamps (silently fails)
# $newReplies = $threadReplies | Where-Object { $_.createdDateTime -gt $lastTime }
```
### Mobile HTML stripping
Teams mobile wraps messages in `<p>` tags. Strip HTML tags from incoming replies before
processing:
```powershell
$text = $reply.body.content -replace '<[^>]+>', ''
```
### CRITICAL: Required message checking implementation
Do NOT write ad-hoc message checking code. Use the exact pattern above — the filter snippet
with message ID comparison is the **required** implementation, not a suggestion.
Common agent mistakes that cause missed messages:
- Writing inline PowerShell that displays only the "last N" replies (`Select-Object -Last 3`)
  instead of filtering all replies by ID
- "Peeking" at the thread with truncated output instead of processing every new reply
- Checking if the reply count changed instead of actually reading the new content
On every message check cycle, the agent must:
1. Get thread replies from `listChannelMessages`
2. Filter to user replies with `[long]$_.id -gt $lastProcessedMessageId` (the exact snippet above)
3. Process **ALL** matching replies chronologically — never truncate or skip
4. Update `$lastProcessedMessageId` to the highest ID processed

The most dangerous bug in phone mode is **the parser silently returning 0 results when
messages exist**. The agent sees "0 new messages" and continues waiting, while the user is
actively posting with no way to know the agent can't see them.
**Mandatory safeguards:**
1. **Null-check the parsed thread object.** If `$thread` or `$thread.replies` is `$null`,
   that is a **parser failure**, not "no messages". Log a warning and retry with the native
   MCP tool as fallback:

   results. The agent must log the error and fall back to the native MCP tool, not silently
   continue.
### Complete Direct HTTP Message Check (reference implementation)
When using direct HTTP after token refresh, use this complete function instead of writing
ad-hoc parsing code. This function handles all known failure modes:
```powershell
function Check-PhoneModeMsgs {
    param(
        [string]$McpUrl,
        [string]$AccessToken,
        [string]$TeamId,
        [string]$ChannelId,
        [string]$ThreadId,
        [long]$LastProcessedId
    )
    $headers = @{
        "Authorization" = "Bearer $AccessToken"
        "Content-Type"  = "application/json"
        "Accept"        = "application/json, text/event-stream"
    }
    $body = @{
        jsonrpc = "2.0"; id = 1; method = "tools/call"
        params = @{
            name = "listChannelMessages"
            arguments = @{ teamId = $TeamId; channelId = $ChannelId; top = 5; expand = "replies" }
        }
    } | ConvertTo-Json -Depth 5
    # Step 1: Make the HTTP call
    try {
        $resp = Invoke-WebRequest -Uri $McpUrl -Method POST -Headers $headers -Body $body
    } catch {
        Write-Warning "HTTP call failed: $_"
        return @{ Success = $false; Error = "HTTP_FAILED"; NewReplies = @() }
    }
    # Step 2: Parse SSE response using the robust parser
    $graphData = Parse-McpSseResponse -RawContent $resp.Content
    if ($null -eq $graphData) {
        Write-Warning "SSE parsing returned null — falling back to native MCP tool"
        return @{ Success = $false; Error = "PARSE_FAILED"; NewReplies = @() }
    }
    # Step 3: Find the thread (Select-Object -First 1 to ensure single object, not array)
    $messages = $graphData.value
    $thread = $messages | Where-Object { $_.id -eq $ThreadId } | Select-Object -First 1
    if ($null -eq $thread) {
        Write-Warning "Thread $ThreadId not found in $($messages.Count) channel messages"
        return @{ Success = $false; Error = "THREAD_NOT_FOUND"; NewReplies = @() }
    }
    # Step 4: Filter new user replies
    if (-not $thread.replies -or $thread.replies.Count -eq 0) {
        $threadAge = $null
        try { $threadAge = (Get-Date) - [DateTime]::Parse($thread.lastModifiedDateTime) } catch {}
        if ($threadAge -and $threadAge.TotalMinutes -lt 30) {
            Write-Warning "Thread modified $([math]::Round($threadAge.TotalMinutes)) min ago but 0 replies parsed"
        }
        return @{ Success = $true; Error = $null; NewReplies = @() }
    }
    # Anchor the bot-prefix match at start (`^🤖`) so user replies that mention the emoji aren't skipped
    $newReplies = @($thread.replies | Where-Object {
        ($_.body.content -replace '<[^>]+>','') -notmatch '^🤖' -and
        [long]$_.id -gt $LastProcessedId
    })
    return @{ Success = $true; Error = $null; NewReplies = $newReplies }
}
```
**Usage in polling loop:**
```powershell
$result = Check-PhoneModeMsgs -McpUrl $mcpUrl -AccessToken $tokens.accessToken `
    -TeamId $teamId -ChannelId $channelId -ThreadId $threadId -LastProcessedId $lastProcessedId
if (-not $result.Success) {
    Write-Warning "Direct HTTP check failed ($($result.Error)) — trying native MCP tool"
    # Fall back to native listChannelMessages tool call
} elseif ($result.NewReplies.Count -gt 0) {
    foreach ($reply in ($result.NewReplies | Sort-Object { [long]$_.id })) {
        $text = $reply.body.content -replace '<[^>]+>', ''
        Write-Output "User message: $text"
        # Process the message...
        $lastProcessedId = [long]$reply.id
    }
}
```
> **Key design principle:** The function returns a structured result with `Success`, `Error`,
> and `NewReplies` fields. A failed parse returns `Success = $false` — it does NOT return
> an empty `NewReplies` array that would be silently treated as "no messages". The caller
> MUST check `Success` before interpreting `NewReplies`.
## Reply Verification
After posting a reply via `replyToChannelMessage`, **always verify the reply was delivered**
before proceeding to notifications or further polling.
### Why this is needed
Direct HTTP calls to the Teams MCP can fail silently — the `Invoke-WebRequest` may return
HTTP 200 but the SSE response may contain an error, or the response parsing may fail,
resulting in no message actually posted. Since phone mode messages are the user's only
communication channel, a silently lost message means the user is waiting indefinitely
with no way to know something went wrong.
### Verification steps
After posting a reply:
1. Call `listChannelMessages` with `expand: "replies"` for the thread.
2. Confirm the reply count increased or that your new reply appears in the thread.
3. If the reply is missing, re-post it.

## Token Refresh
The Teams MCP OAuth token expires after ~75 minutes. Detect and refresh proactively.
### Detect expiry
Check `~/.copilot/mcp-oauth-config/` for `.tokens.json` files. Match to the config whose
`.json` has `serverUrl` containing `mcp_TeamsServerV1`. The `expiresAt` field is a Unix
timestamp (seconds since epoch). Refresh if within 10 minutes of expiry.
### Refresh token
```powershell
$config = Get-Content "$env:USERPROFILE/.copilot/mcp-oauth-config/<config>.json" | ConvertFrom-Json
$tokens = Get-Content "$env:USERPROFILE/.copilot/mcp-oauth-config/<config>.tokens.json" | ConvertFrom-Json
$body = @{
    client_id     = $config.clientId
    grant_type    = "refresh_token"
    refresh_token = $tokens.refreshToken  # camelCase property
    scope         = $tokens.scope
}
$response = Invoke-RestMethod -Method Post `
    -Uri "https://login.microsoftonline.com/common/oauth2/v2.0/token" `
    -ContentType "application/x-www-form-urlencoded" `
    -Body $body
# Write back with camelCase property names
$tokens.accessToken = $response.access_token
$tokens.refreshToken = $response.refresh_token
$tokens.expiresAt = [long]([DateTimeOffset]::UtcNow.AddSeconds($response.expires_in).ToUnixTimeSeconds())
$tokens | ConvertTo-Json | Set-Content "<tokens-file-path>"
```

### Robust SSE Response Parsing (CRITICAL)
Direct HTTP calls return SSE-formatted responses that contain **triple-nested JSON** with
unicode escaping (`\u0022` instead of `"`). Ad-hoc regex-based parsing is the #1 cause of
silently missed messages. **Always use `ConvertFrom-Json`** — never regex — to extract data.
**Known failure modes:**
- Large responses (250KB+) may be saved to temp files with full unicode escaping — regex
  patterns like `-match '"id"'` fail because the file contains `\u0022id\u0022` instead
- SSE `data:` lines may be split across multiple lines in large responses
- The JSON-RPC `result.content[0].text` field contains a JSON **string** (not object) that
  itself contains another JSON string — requiring 3 levels of `ConvertFrom-Json`
**Required parsing function** — use this exact implementation, not an ad-hoc version:
```powershell
function Parse-McpSseResponse {
    param([string]$RawContent)
    # Step 1: Extract the last SSE message block containing a result
    $blocks = $RawContent -split 'event: message\r?\n'
    # Match the JSON-RPC envelope strictly — `-match 'result'` would match user content
    $resultBlock = $blocks | Where-Object { $_ -match '"jsonrpc":\s*"2\.0"' } | Select-Object -Last 1
    if (-not $resultBlock) {
        Write-Warning "SSE: No result block found in response"
        return $null
    }
    # Step 2: Extract and join all data: lines (handles multi-line splits)
 
Part 3/3 (lines 529-791)
    $dataLines = ($resultBlock -split '\r?\n' | Where-Object { $_ -match '^data: ' }) -replace '^data: ', ''
    $jsonStr = $dataLines -join ''
    if (-not $jsonStr -or $jsonStr.Length -lt 10) {
        Write-Warning "SSE: Empty or too-short data payload (len=$($jsonStr.Length))"
        return $null
    }
    # Step 3: Parse the triple-nested JSON — ConvertFrom-Json handles \u0022 natively
    try {
        $rpc = $jsonStr | ConvertFrom-Json                          # Level 1: JSON-RPC envelope
        $textWrapper = $rpc.result.content[0].text | ConvertFrom-Json  # Level 2: {message, response}
        $graphData = $textWrapper.response | ConvertFrom-Json         # Level 3: Graph API response
        return $graphData
    } catch {
        Write-Warning "SSE parse failed at JSON level: $_"
        Write-Warning "Raw payload length: $($jsonStr.Length) chars"
        return $null
    }
}
```

> **NEVER use regex to extract message IDs, reply content, or reply counts from raw SSE
> responses.** The unicode-escaped format (`\u0022id\u0022: \u00221776546275915\u0022`)
> breaks all regex patterns. `ConvertFrom-Json` decodes unicode escapes automatically.
### Handling SSE response parsing failures
When parsing the SSE response from direct HTTP calls:
- If `ConvertFrom-Json` fails on the response data, the message may or may not have posted.
  **Do not assume success.** Verify delivery via `listChannelMessages` (see Reply Verification).
- If the response contains an error in the JSON-RPC result, log the error and retry.
- Never combine the reply posting and notification into a single try/catch block — a parsing
  failure after a successful post should not prevent the notification, and vice versa.
## Message Format
**All Teams messages** (not just phone mode) must follow these rules:
### Content type
Always use `contentType: "html"`. Never use `contentType: "text"` — it renders as an
unformatted wall of text with no line breaks.
### AI agent identity
Always identify as an AI agent. Recipients see the user's name (delegated auth), so the prefix
is the only differentiator.
- **Prefix**: Always start messages with `🤖 [Copilot]: `
- **DMs/group chats**: Start with `"Hi [Name], this is [User]'s AI agent (Copilot)."`
### HTML formatting guidelines
- `<h3>` for section headers
- `<ul><li>` for bullet lists, `<ol><li>` for numbered lists
- `<b>` for bold, `<em>` for emphasis
- `<br>` for line breaks between sections
- Minimal emoji — use for section markers only, not inline decoration
## Notifications via Phone Mode Notifier Agent
Phone mode uses delegated auth, so Teams does not notify the user when the Copilot agent
posts (since it appears as the user themselves). To get mobile notifications, phone mode uses
a **Copilot Studio agent** called **Phone Mode Notifier** as a notification relay.
### How it works
1. After posting a reply in the phone mode channel thread, send a short notification message
   to the bot's 1:1 chat.
2. The bot responds with an acknowledgment → Teams sends a push notification to the user.
3. The notification message includes a **deep link** so the user can tap through directly to
   the channel reply.
### Configuration
Read the **Notifier Bot Chat ID** from `~/.copilot/copilot-instructions.md` (in the phone mode
section, under Channel Info). This is a required field — if it says `<BOT_CHAT_ID>` or is
missing, tell the user to run the `setup-phone-mode` skill to complete setup before activating
phone mode.
### After each channel reply (verified)
After posting a reply via `replyToChannelMessage` **and verifying it was delivered** (see
Reply Verification section), construct a deep link using the confirmed reply message ID
and send a notification ping:
> **Do NOT send notifications before verifying the reply landed.** A notification with a
> broken deep link (empty or wrong reply ID) wastes the user's attention and erodes trust
> in phone mode.
```
Deep link format:
https://teams.microsoft.com/l/message/{channelId}/{replyMessageId}?groupId={teamId}&parentMessageId={threadId}
```
Where `{threadId}` is the ID of the top-level thread post (the message created in
Activation step 1). Without `parentMessageId`, Teams cannot resolve the reply within the
thread and the link appears broken (shows empty or "message not found").
Send to the bot chat:
```
📱 Phone Mode reply in: {threadTitle}
View: {deepLink}
```
Where `{threadTitle}` is the top-level post title (the title you used when creating the thread
in Activation step 1). This gives the user context about which phone mode session has a new
reply, especially useful when multiple sessions are active.
Use `contentType: "html"` and format as:
```html
📱 <b>Phone Mode reply in: {threadTitle}</b><br><a href="{deepLink}">View reply in channel</a>
```
### Important notes
- Send notifications for **every** channel reply, not just the first one.
- The bot chat is a 1:1 chat that already exists after the user installs the agent during setup.

## Teams MCP Tips
### Formatting messages for humans
**ALWAYS use `contentType: "html"` when sending ANY Teams message** — whether it's a DM, group
chat, channel post, or phone mode reply. Plain text (`contentType: "text"`) renders as an
unformatted wall of text in Teams with no line breaks, bullets, or structure. **Never use
`contentType: "text"` for Teams messages.**
Format messages with HTML for readability:
- Use `<h3>` for section headers
- Use `<ul><li>` for bullet lists and `<ol><li>` for numbered lists
- Use `<b>` for bold and `<em>` for emphasis
- Use `<br>` for line breaks between sections
- Keep emojis minimal — use them for headers/section markers only, not inline decoration
- Avoid sending large walls of plain text — structure content so it's scannable
### Time zone
When communicating dates and times to the user (in Teams messages, reports, ETAs, etc.),
always use the **local machine time zone** — never UTC. Detect it with
`[System.TimeZoneInfo]::Local` in PowerShell. Convert UTC timestamps to local time using
`[TimeZoneInfo]::ConvertTimeFromUtc($utc, [TimeZoneInfo]::Local)` or
`([DateTimeOffset]$utc).ToLocalTime()`. Users read messages on their phone and shouldn't
have to mentally convert from UTC.
### Finding people by name
The Teams MCP tools require a **UPN** (User Principal Name). UPN ≠ primary email at Microsoft
(e.g., primary email `Inbar.Rotem@microsoft.com` vs UPN `inrotem@microsoft.com`).
Use **WorkIQ** to resolve names to emails/aliases:
1. Ask WorkIQ: *"Who is Anna that I recently chatted with? What is her email and alias?"*
2. Use the returned UPN with Teams MCP tools.
3. If the call fails with "user not found", try the alias format.
### Sending messages to the right person
- Use `createChat` (not `listChats`) to find or create a 1:1 chat — it returns the existing
  chat if one exists, guaranteeing the correct recipient.
- If you used `listChats`, verify the recipient with `listChatMembers` before sending.
### Finding a meeting chat by meeting name
The `listChats` API does not reliably return old or inactive meeting chats. To find a meeting's
chat thread ID, use the **Calendar MCP** (`mcp_CalendarTools`) via direct HTTP:
```powershell
$body = @{
    jsonrpc = "2.0"; id = 1; method = "tools/call"
    params = @{
        name = "ListEvents"
        arguments = @{
            meetingTitle = "<MEETING_NAME>"
            startDateTime = "<SEARCH_START_ISO8601>"
            select = "subject,onlineMeeting"
        }
    }
} | ConvertTo-Json -Depth 5
```
Call the Calendar MCP endpoint at:
`https://agent365.svc.cloud.microsoft/mcp/environments/<ENV_ID>/servers/mcp_CalendarTools`
The response includes `onlineMeeting.joinUrl` which contains the chat thread ID. Extract it:
```powershell
# joinUrl looks like: https://teams.microsoft.com/l/meetup-join/19%3ameeting_<ID>%40thread.v2/...
# URL-decode to get: 19:meeting_<ID>@thread.v2
$chatId = [System.Web.HttpUtility]::UrlDecode(($joinUrl -split '/')[4])
```
Use the extracted chat ID with Teams MCP tools (`postMessage`, `listChatMessages`, etc.).
> **Note:** The Calendar MCP server URL uses the same environment ID as the Teams MCP. Read it
> from `~/.copilot/mcp-config.json` (the `teams` entry URL contains the environment ID).

### Upgrade Flow
When an existing phone mode section doesn't match the current template, the agent should
**reconcile** the user's config with the latest template:
1. **Read** the current phone mode section from `~/.copilot/copilot-instructions.md`.
2. **Read** the Custom Instructions Template from the `phone-mode` skill at
   `~/.copilot/installed-plugins/dsp-ai-marketplace/dsp-skills/skills/phone-mode/SKILL.md`.
3. **Extract** any real (non-placeholder) values from the user's existing config — Team ID,
   Channel ID, Bot Chat ID, or any other configured values.
4. **Replace** the user's entire phone mode section with the template from the skill.
5. **Substitute** the extracted real values back into the template, keeping placeholders for
   anything that wasn't configured yet.
6. **Run the appropriate phase** for any remaining placeholders (e.g., Phase 3 if Bot Chat ID
   is still a placeholder).
This approach ensures the copilot-instructions.md always reflects the latest skill template
structure, regardless of what changed between versions. The agent doesn't need to know what
